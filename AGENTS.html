技术博客写作约束 ​

blog/ 下的文章统一遵循 docs/workflows/blog-writing-style.md 中的博客写作规范。新增或大幅改写文章前，应先读取该规范。

blog/ 目录下的所有内容都应该保持高信息密度：

  • 尽量减少低信息密度的过渡句、重复解释和空泛表述
  • 优先把关键信息直接写进标题、列表、表格、代码注释和配置注释中
  • 能用一行注释说清的内容，不要再在代码块后重复解释一遍
  • 示例要尽量“可直接使用”，避免为了凑篇幅添加冗余文字
  • 在不影响可读性的前提下，优先压缩篇幅、提高单位段落的信息量

新增板块 vs 新增内容 ​

  • 新增板块（如新增一个中间件、一个新主题分类）：需要同步更新 blog/cards/ 卡片列表、.vitepress/config/sidebar/ 侧边栏配置、public/icons/ 图标文件
  • 已有板块下新增内容（如在已有 Redis 分类下新增一篇数据类型文章）：编写 .md 文件的同时，必须同步更新 .vitepress/config/sidebar/internal/ 对应的侧边栏配置，将新页面加入导航。完成后执行 docs:build 验证构建；只有涉及视觉表现时才需要浏览器预览。

知乎回答读取命名规范 ​

通过 CDP 从知乎页面读取回答并保存为本地 Markdown 时，文件名遵循以下格式：

bash
zhihu_{questionId}_{answerId}-{questionTitle}-{author}.md
  • questionId：知乎问题 ID，从问题 URL 中提取
  • answerId：知乎回答 ID，从回答链接 URL 中提取
  • questionTitle：问题标题，去掉特殊符号
  • author：回答作者的用户名

同时，在回答文件同目录下生成一份摘要文件 zhihu_{questionId}_{questionTitle}.md，汇总本次读取的所有回答概览。

知乎资料从采集到博客发布的完整步骤，遵循仓库级 docs/workflows/zhihu-content-production.md。

Build, Lint, and Test Commands ​

blog/ 目录对应的文档站点使用 package.json 中的 docs:* 命令进行验证。目前可用命令：

  • npm run docs:dev：启动 VitePress 开发服务器，适合边改边看
  • npm run docs:build：执行生产构建，检查文档站点是否可以成功构建
  • npm run docs:preview：预览构建产物，适合检查最终页面效果

每次修改 blog/ 下的内容后，都应该至少执行一次相关验证命令。普通文章文字、Markdown 结构和 frontmatter 修改默认不启动浏览器：

  • 优先使用 package.json 中已有的 docs:* 命令进行验证
  • 能运行构建时，至少执行一次 npm run docs:build
  • 只修改文章内容且不涉及视觉表现时，执行 npm run docs:lint 和 npm run docs:build 即可
  • 如果本次修改涉及 Mermaid、图片、布局、样式或页面交互，再补充执行 npm run docs:dev 并进行浏览器预览
  • 如果需要检查构建后的最终页面表现，可以执行 npm run docs:preview；该命令本身不会自动启动浏览器
  • 如果因为环境、依赖或时间限制无法验证，必须在最终说明里明确指出未验证及原因

浏览器验证 ​

浏览器预览不是修改 blog/ 后的默认步骤。只有以下情况才需要启动浏览器：

  • 修改 Mermaid 图表，或调整主题、样式、布局和页面交互
  • 新增或替换图片，并需要确认尺寸、裁剪、加载或暗色模式表现
  • 修改链接、侧边栏或目录结构，并需要确认页面跳转、导航或路由表现
  • 用户明确要求检查页面视觉效果

仅修改普通文章文字、Markdown 结构、frontmatter 或代码示例时，不启动浏览器，使用 Markdown 检查和 VitePress 构建即可。

需要浏览器预览时，按下面的顺序验证：

  • 预览文档站一律使用普通 Chrome（临时 profile），不要启动 Edge Beta；edge-beta-cdp 只用于需要复用登录态的知乎等任务。

  • 如果已在后台启动 npm run docs:dev，直接按下面的 Chrome 步骤预览即可，不需要再启动任何浏览器 Skill；确认无残留调试实例后启动 Chrome 再连接 9222。

  • 先执行 npm run docs:build，确认 VitePress 可以成功构建，这是最基本的通过条件

  • 构建通过后，使用 agent-browser 以有头模式打开 Chrome 进行页面预览验证：

    bash
    # 1. 确保没有残留 Chrome 调试实例
pkill -f 'Google Chrome.*remote-debugging-port' 2>/dev/null

# 2. 直接启动 Chrome（使用临时 profile，不要用 open 命令）
/Applications/Google\ Chrome.app/Contents/MacOS/Google\ Chrome \
  --remote-debugging-port=9222 \
  --user-data-dir="/tmp/chrome-test-profile" \
  --no-first-run \
  --new-window "about:blank" &

# 3. 启动 dev server
npm run docs:dev &

# 4. 连接 agent-browser 并打开目标页面
npx agent-browser connect 9222
npx agent-browser open http://localhost:5173/<path>
npx agent-browser wait 2000
npx agent-browser snapshot -i -c

  • 测试 Chrome 必须使用独立临时 profile（--user-data-dir），不得复用用户默认浏览器配置、登录态、扩展或历史数据

  • macOS 下必须直接通过 Chrome 二进制路径启动，不得使用 open 命令（open 会路由到已有 Chrome 会话，导致 --remote-debugging-port 失效）

  • 不得仅以 snapshot、DOM 输出、无头截图或命令行结果代替页面预览验证

  • 不要因为普通文案或 Markdown 结构修改而启动浏览器；只有上面列出的视觉或交互风险需要页面预览

  • 如果因为环境、时间或依赖问题无法完成验证，必须在最终说明中明确写出未验证项和原因

  • 验证完成后，关闭测试 Chrome 窗口（pkill -f 'Google Chrome.*remote-debugging-port'），无残留 profile
